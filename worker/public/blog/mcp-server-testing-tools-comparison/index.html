MCP server testing tools compared: Inspector, scanners, and CI gates

TL;DR: There is no single "MCP testing tool." The official MCP Inspector is the debugger: it connects, lists tools, and calls them. Browser testers such as MCP Playground do a similar job for remote HTTP servers. Security scanners (TrueFoundry, MCP Scanner, Snyk Agent Scan, and parts of CheckMCP) probe for injection, poisoning, and misconfiguration, sometimes by sending payloads or invoking tools. MCP Readiness is a live surface scan and CI gate: OAuth discovery, Origin and CORS, annotations, JSON-RPC hygiene, and the token cost of tools/list, without calling your tools. Use Inspector (or a playground) for behavior, a readiness scan in CI for regressions, and a security scanner when you need an adversarial pass.

"MCP testing" is used for at least three jobs: does the protocol work, will this hurt an agent's context or a client's auth flow, and can an attacker abuse the tools. Tools that excel at one of those jobs are routinely asked to do the other two. This comparison sticks to what each product documents, and uses our 20 November 2026 unauthenticated scans of 23 popular remote servers (comparison page) only as a reminder of what a surface scan actually finds.

The jobs, not the brands

Interactive debugging. You are writing a tool. You need to send initialize, inspect tools/list, call the tool with valid and invalid arguments, and read the JSON-RPC frames. This is Inspector's home ground, and it is also what in-browser testers are built for.

Interoperability and cost. You are about to merge. You want a failing check if Origin validation disappeared, if OAuth discovery regressed to the 2025-03-26 shape, if a description ballooned to thousands of characters, or if unknown methods no longer return JSON-RPC -32601. Those are leftovers we still see on well-known servers: in the 20 November 2026 set, three of eight open servers had at least one overly long description (Hugging Face's list costs about 4,967 tokens per turn); AWS Knowledge did not return -32601 for unknown methods; Atlassian still used legacy OAuth discovery.

Security review. You want a second opinion on tool poisoning, injection, secret leakage, and auth bypass. That is a different threat model. Some scanners send live payloads or invoke read-only tools to see what comes back. That can be the right test, and it is not something a metadata-only scan should pretend to be.

The tools

MCP Inspector (docs, source). The official Model Context Protocol developer tool, shipped as @modelcontextprotocol/inspector. It has a browser UI, a scriptable CLI, and a terminal UI on one binary. You can launch it against a local stdio server (npx @modelcontextprotocol/inspector node path/to/server/index.js) or use --cli --method tools/list (and tools/call) in a pipeline. The CLI also supports load tests with latency thresholds. Inspector speaks the same transports and OAuth flow across clients. It does not publish a 0–100 readiness score, and it does not, by itself, fail a PR when your tool list grows by two thousand tokens.

MCP Playground Server Tester (mcp-server-tester). A free in-browser tester for remote HTTP, SSE, and Streamable HTTP servers. You paste a URL, add a bearer token if needed, then explore tools, prompts, and resources and inspect JSON-RPC. It is aimed at "validate before you ship" in the same sense as Inspector's web UI. The site notes that stdio servers cannot be spawned from the browser and points those users at Inspector. It is a client, not a CI readiness gate.

MCP Readiness (hosted scan, GitHub Action). Our open-source scanner. It connects the way a client does and scores the live surface: OAuth discovery (RFC 9728 and RFC 8414, plus detection of the 2025-03-26 legacy flow), tool annotations, Origin and CORS, schemas, JSON-RPC hygiene, and an estimate of how many tokens tools/list costs on every agent turn. The public scan does not call tools. The free GitHub Action can fail a job with fail-under and max-context-tokens against a server started on localhost in CI. Scoring starts at 100, minus 15 per failing check and minus 5 per warning. It is a surface scan, not a penetration test.

TrueFoundry MCP Security Scanner (sec-scan). A credential-free scan of a public MCP URL. TrueFoundry describes coverage across transport security, authentication, MCP protocol conformance, injection, CORS and headers, resilience, and information disclosure. Use it when you want a security-oriented pass on a public endpoint. It is not a substitute for Inspector's interactive tools/call workflow, or for a token-budget CI gate.

MCP Scanner (mcpscanner.dev). A free security scanner that accepts a live HTTP or SSE URL or a static MCP client config. The product describes 30+ checks, including handshake, tool enumeration, live injection probes, auth bypass, and config static analysis, and it returns an A–F grade with findings. Because it fires payloads at parameters, treat it as an adversarial test you run on a server you own or are authorized to test — not as a casual debug client.

CheckMCP (checkmcp.dev). An audit that produces an MCP Score out of 100 across several pillars, including security, tool design, schemas, context cost, and compliance (protocol version, annotations, JSON-RPC errors, OAuth discovery). The site and CLI document an optional behavioral mode that invokes read-only tools with canary inputs to look for prompt injection and leakage in tool output. The CLI (audit-mcp) supports --min-score for CI. Overlap with MCP Readiness is real on context cost and discovery; the behavioral evals and OWASP-style security pass are the difference. If you use both, do not treat the two scores as interchangeable.

Snyk Agent Scan (GitHub). A local discovery and security scanner for agent setups. It finds MCP servers, skills, and agent configs on the machine (Claude, Cursor, and others) and looks for prompt injection, tool poisoning, and related issues in tool descriptions and configuration. Snyk warns that retrieving tool descriptions can start stdio servers or call remote URLs, and it asks for consent in interactive runs. This is the right shape of tool for "what did I just install on this laptop," not for gating a server repository's pull requests.

How to combine them

A practical pre-ship setup is three layers, not one "winner":

  1. Inspector or MCP Playground while you implement a tool, and at least once before release, for real tools/call behavior.
  2. A readiness and token-cost gate in CI, such as the MCP Readiness Action, so Origin, OAuth discovery, annotations, error codes, and list size cannot regress unnoticed.
  3. A security scanner you are authorized to run, on a staging URL, when you change tools that take rich input or run on untrusted data.

If you only have time for one automated check today, add the CI gate: it is the layer most teams skip, and it is the layer that would have flagged most of the open issues on the popular-server table. Then scan your own URL once so you know the baseline the gate will protect.

FAQ

Which tool should I use first if I am new to MCP?
Start with MCP Inspector. It is official, it works with stdio and HTTP, and it will show you the exact JSON-RPC your server emits. Add a hosted or CI scanner after your first successful tools/call.

Why do two scanners give different scores for the same server?
They are not measuring the same things, and they do not use the same weights. A security scanner that sends injection payloads can fail a server that looks clean on a metadata-only readiness scan, and a readiness scan can fail a server that looks fine in a chat client because Origin is not validated or tools/list is huge. Compare findings, not the integer.

Does MCP Readiness replace a security scanner?
No. The public scan and the free Action do not call tools and do not fire injection payloads. They will flag some security-relevant surface issues (missing annotations, open Origin, broken OAuth discovery), but they are not a substitute for an adversarial review.

Can I run all of this in GitHub Actions?
Yes, in parts. Inspector's CLI can assert tools/list or call a smoke-test tool. The MCP Readiness Action can fail on a score or a token budget against localhost. CheckMCP's CLI documents --min-score. Security scanners that send live payloads should be aimed at a staging server you control, with explicit authorization, not at a production URL you do not own.
